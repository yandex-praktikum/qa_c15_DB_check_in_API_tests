# Проект спринта 7. DB-check в API-тестах Самоката

## Контекст

Ты — автоматизатор в команде Самоката.

У команды уже есть API-тесты, которые проверяют основные сценарии работы сервиса. Тесты из предыдущих спринтов умеют проверять ответы API, используют фикстуры, изоляцию данных и отчётность.
Но появился новый запрос от команды:

> Нужно убедиться, что после выполнения API-операции данные в базе действительно находятся в ожидаемом состоянии.

Сейчас тест может показать:
- API вернул успешный ответ;
- операция считается выполненной;

но это не гарантирует, что данные в базе изменились правильно.
Твоя задача — добавить проверку состояния базы данных в существующий тестовый сьют.

---

# Что нужно сделать

Важно:

**Новый сьют писать не нужно.**
Доработай готовый тест удаления курьера test_delete_courier.py.
Твой результат должен показать, что автотест проверяет не только ответ API, но и фактическое состояние данных.

# Задача

В проекте есть сценарий:
1. Создается курьер.
2. Для него создаются заказы.
3. Выполняется удаление курьера через API.
4. Проверяется состояние базы данных.

Нужно проверить:
- что API вернул успешный ответ;
- что связанные данные в базе находятся в ожидаемом состоянии.

# Частые ошибки

## Тест написан с конкретным id

Плохо: DELETE courier/1

Почему: после первого запуска данные изменятся.
Используй подготовку данных через фикстуры.

---

## DB-check повторяет API

Например:
API вернул: 200 OK
и тест проверяет только: status_code == 200
Это не проверка базы.

---

## SQL собирается через f-string

Плохо:
query = f"SELECT * FROM orders WHERE id={order_id}"

Используй параметры запроса.
Нет очистки данных.
Если тест создал данные, он должен их убрать.
Иначе следующий запуск может зависеть от предыдущего.

## Важное замечание
Если DB-check показывает расхождение между API и базой — это не обязательно ошибка теста.
Автотест должен фиксировать фактическое поведение системы.
Если сервис возвращает успешный ответ, но состояние базы не соответствует ожиданиям, это повод зарегистрировать дефект.
