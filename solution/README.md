# Назначение проекта

Этот репозиторий содержит эталонное решение проекта спринта 7.

Цель проекта: добавить в существующий API-тестовый сьют проверку состояния базы данных и научиться находить расхождения между поведением API и фактическими данными.

В проекте используется сценарий:
- создание курьера;
- создание связанных заказов;
- удаление курьера через API;
- проверка состояния базы данных.

## DB-check

В тест удаления курьера добавлена проверка:

orders = db.get_orders_by_courier(courier_id)
assert orders == []

Проверка выполняется напрямую через базу данных.
Она не дублирует API-ответ.

Проверяемый сценарий

Тест:
создает курьера;
создает связанные заказы;
удаляет курьера через API;
проверяет состояние таблицы orders.
Ожидаемый результат

При запуске: pytest тест DB-check падает.

Это ожидаемое поведение.

Почему тест падает

API сообщает: DELETE /courier/{id}
200 OK

Однако после удаления курьера связанные заказы остаются в базе.

Пример:

couriers
id
---
5

orders

id | courier_id
--------------
10 | 5
11 | 5

То есть сервис нарушает ожидаемое поведение: после удаления курьера связанные данные должны быть обработаны согласно требованиям сервиса.

Важно: тест НЕ должен быть изменен, чтобы проходить.

Красный результат означает: автоматизированная проверка обнаружила дефект приложения.

## Диагностика

Для анализа используется запрос:
SELECT
    id,
    track,
    status
FROM orders
WHERE courier_id = :courier_id;

Запрос показывает, что связанные заказы остались после удаления курьера.

## Подготовка через БД + очистка через БД

Почему: 
тестам нужны контролируемые данные;
создание тестового состояния через API увеличивает время выполнения;
база позволяет быстро подготовить необходимые связи;
очистка после тестов предотвращает влияние сценариев друг на друга.
Почему не только API

API подходит для проверки пользовательских сценариев.
Но в этом проекте задача — проверить внутреннее состояние данных.
Поэтому используется дополнительный DB-check.

## Проверка ревьюером

Ревьюер должен убедиться:

SQL параметризован;
нет хардкода id;
данные создаются перед тестом;
данные удаляются после теста;
соединения закрываются;
README позволяет повторить запуск;
DB-check проверяет состояние базы.
